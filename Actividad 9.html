1. Nombre del laboratorio

File path traversal, traversal sequences stripped non-recursively — PortSwigger Web Security Academy.

2. Nivel

Apprentice (Aprendiz).

3. Tipo de explotación

Path Traversal (Directory Traversal) mediante evasión de filtros no recursivos, permitiendo la lectura de archivos locales del servidor.

4. Objetivo del laboratorio

Explotar una vulnerabilidad de Path Traversal en una aplicación web que utiliza el parámetro filename para cargar imágenes de productos.

La aplicación implementa un mecanismo de seguridad que elimina las secuencias de retroceso de directorios (../), pero realiza esta validación de manera no recursiva.

El objetivo principal es evadir este filtro mediante secuencias de navegación anidadas para acceder al archivo /etc/passwd del servidor Linux y recuperar información relacionada con las cuentas de usuario del sistema.

5. Explicación técnica de la vulnerabilidad

La vulnerabilidad Path Traversal ocurre cuando una aplicación web utiliza rutas de archivos proporcionadas por el usuario sin aplicar las validaciones de seguridad necesarias.

En este laboratorio, la aplicación utiliza el parámetro filename dentro de una petición HTTP GET para recuperar imágenes almacenadas en el servidor. 

GET /image?filename=40.jpg

Aunque existe un mecanismo que elimina las secuencias de retroceso (../), este filtro se ejecuta una sola vez y no vuelve a analizar el resultado.

Esta debilidad permite utilizar secuencias anidadas como ....//, que contienen internamente el patrón ../.

Cuando el filtro elimina dicho patrón, la cadena resultante se convierte en ../. Debido a que no se realiza una segunda validación, la aplicación termina procesando una ruta que permite retroceder entre directorios. 

....//  →  ../

Como resultado, es posible acceder a archivos ubicados fuera del directorio autorizado, incluyendo recursos sensibles del sistema operativo como /etc/passwd.

  1. Se ingresó al laboratorio de PortSwigger Web Security Academy y se verificó que su estado inicial fuera "Not solved".

  3. Mediante Burp Suite, se accedió a Proxy → HTTP history, con la intercepción desactivada, y se identificó la petición: 
    GET /image?filename=40.jpg
  4. Se envió la petición a la herramienta Repeater para analizar su contenido y comprobar la respuesta original del servidor.

    ....//....//....//....//etc/passwd
  6. Se presionó el botón Send para enviar la petición modificada al servidor.
  7. El servidor respondió con el código HTTP 200 OK, mostrando el contenido del archivo /etc/passwd, incluyendo registros correspondientes a las cuentas de usuario del sistema Linux.
  8. Finalmente, se regresó al navegador y se verificó que el laboratorio había cambiado su estado a "Solved", confirmando que la vulnerabilidad fue explotada exitosamente.

8. Explicación del payload

El payload utilizado fue:

....//....//....//....//etc/passwd

Funcionamiento

  • ....//: Es una secuencia de navegación anidada que contiene internamente el patrón ../.
  • ../: Permite retroceder un nivel dentro de la estructura de directorios del servidor.
  • ....//....//....//....//: Repite cuatro veces la secuencia anidada para intentar retroceder cuatro niveles una vez aplicado el filtro.
  • etc/passwd: Identifica el archivo del sistema Linux al que se desea acceder.

La explotación funciona porque el servidor elimina la primera coincidencia de ../ dentro de cada secuencia ....//, dejando como resultado una nueva secuencia ../. 

Entrada:  ....//

Filtro:   Elimina ../

Resultado: ../

Debido a que el filtro no realiza una validación recursiva, estas nuevas secuencias permanecen en la ruta final y permiten navegar hacia directorios superiores.

Al repetir el patrón cuatro veces, es posible salir del directorio de imágenes y alcanzar la ubicación del archivo /etc/passwd.

Como resultado, el servidor devuelve el contenido del archivo solicitado en lugar de una imagen, confirmando la existencia de la vulnerabilidad.

9. Mitigación recomendada

Para prevenir vulnerabilidades de Path Traversal mediante evasión de filtros no recursivos, se recomiendan las siguientes medidas:

  1. Validación de entradas: Evitar que los parámetros proporcionados por el usuario contengan secuencias de navegación de directorios o rutas no autorizadas.
  2. Listas de archivos permitidos: Restringir el acceso únicamente a archivos previamente autorizados, utilizando identificadores internos en lugar de rutas proporcionadas directamente por el usuario.
  3. Validación de rutas canónicas: Resolver la ruta real del archivo solicitado y comprobar que permanezca dentro del directorio autorizado, incluso después de aplicar procesos de normalización.
  4. Evitar filtros no recursivos: No depender únicamente de la eliminación de patrones como ../, ya que pueden evadirse mediante secuencias anidadas o representaciones alternativas.
  5. Control de permisos: Aplicar el principio de mínimo privilegio para limitar los archivos y directorios a los que puede acceder el proceso del servidor web.
