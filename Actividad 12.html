1. Nombre del laboratorio

File path traversal, validation of file extension with null byte bypass

Traducción: Salto de ruta de archivos con validación de extensión evadida mediante byte nulo.

Laboratorio perteneciente a PortSwigger Web Security Academy.

2. Nivel

Apprentice (Aprendiz)

3. Tipo de explotación

Path Traversal / Directory Traversal mediante Null Byte Injection.

La explotación combina secuencias de recorrido de directorios como ../ con la inyección de un byte nulo, representado mediante URL Encoding como %00.

El objetivo es evadir una validación que exige que el nombre solicitado termine con una extensión de imagen válida, como .jpg.

4. Objetivo del laboratorio

Explotar una vulnerabilidad de Path Traversal presente en el parámetro filename, utilizado por la aplicación para recuperar imágenes almacenadas en el servidor.

La aplicación exige que el nombre solicitado termine con:

.jpg

Para superar esta validación se utiliza un Null Byte Bypass, permitiendo solicitar el archivo:

/etc/passwd

El laboratorio demuestra que una validación basada únicamente en la extensión puede ser insuficiente cuando diferentes capas de una aplicación procesan una misma cadena de forma distinta.

5. Explicación técnica de la vulnerabilidad

La aplicación utiliza el parámetro filename para indicar qué archivo debe recuperar. Una petición legítima puede verse así:

GET /image?filename=51.jpg HTTP/2

Como mecanismo de seguridad, la aplicación comprueba que el valor recibido termine en una extensión de imagen permitida, por ejemplo .jpg.

Sin embargo, permite introducir secuencias de recorrido de directorios:

../

y también procesa un carácter nulo representado como:

%00

En determinados entornos vulnerables, la lógica de validación y la capa que finalmente accede al sistema de archivos pueden interpretar la misma cadena de forma diferente.

../../../etc/passwd%00.jpg
../../../etc/passwd%00.jpg Cadena recibida por la aplicación
↓
.jpg La validación detecta una extensión permitida
↓
%00 El carácter NUL actúa como terminador en una capa vulnerable
↓
../../../etc/passwd Ruta procesada por el componente vulnerable

El resultado es el acceso a un archivo situado fuera del directorio autorizado, a pesar de que la cadena original aparentemente cumple con la validación de extensión.

6. Procedimiento paso a paso

  1. Acceder al laboratorio desde PortSwigger Web Security Academy.
  2. Iniciar Burp Suite y utilizar el navegador configurado con el proxy de Burp.
  3. Seleccionar un producto para generar una solicitud de carga de imagen.
  4. Localizar en Proxy → HTTP history una petición similar a: 
    GET /image?filename=51.jpg HTTP/2
  5. Enviar la solicitud a Burp Repeater.
  6. Enviar primero la petición original para verificar el comportamiento normal de la aplicación.
  7. Modificar el parámetro filename utilizando: 
    ../../../../etc/passwd%00.jpg
  8. Enviar la solicitud modificada: 
    GET /image?filename=../../../../etc/passwd%00.jpg HTTP/2
  9. Comprobar en la respuesta que aparece contenido correspondiente a /etc/passwd.
  10. Regresar al navegador y verificar que el laboratorio cambia de Not solved a Solved.
Nota: la cantidad exacta de secuencias ../ depende de la ubicación desde la que la aplicación resuelve originalmente los archivos. En esta práctica se documentan cuatro porque corresponden al payload utilizado.

8. Explicación del payload

El payload utilizado fue:

../../../../etc/passwd%00.jpg

Secuencia de recorrido de directorios

../../../../

Cada secuencia ../ indica que se debe acceder al directorio padre. Al repetirla varias veces se intenta salir del directorio destinado a las imágenes.

Archivo objetivo

etc/passwd

Corresponde al archivo que se pretende leer en el sistema Linux.

Byte nulo

%00

Es la representación mediante URL Encoding del carácter NUL. En una capa vulnerable puede actuar como terminador de cadena, haciendo que la parte posterior no sea utilizada al acceder al sistema de archivos.

Extensión de imagen

.jpg

La extensión se conserva para cumplir con la validación superficial implementada por la aplicación.

Extensión.jpg

Conceptualmente:

../../../../etc/passwd%00.jpg
                  ↓
        ../../../../etc/passwd

9. Mitigación recomendada

  • Evitar utilizar rutas proporcionadas directamente por el usuario: utilizar identificadores internos y asociarlos con archivos previamente autorizados.
  • Aplicar listas blancas: aceptar únicamente archivos o nombres expresamente permitidos.
  • Normalizar y canonicalizar la ruta: resolver la ubicación final del archivo antes de comprobar si está autorizado.
  • Rechazar caracteres NUL: bloquear caracteres nulos y representaciones como %00.
  • Validar después de decodificar: realizar la decodificación y normalización antes de aplicar los controles de seguridad.
  • Mantener actualizado el entorno de ejecución: utilizar versiones modernas y soportadas del lenguaje, framework y bibliotecas.
  • Aplicar el principio de menor privilegio: limitar los permisos del proceso del servidor web.
Conclusión de seguridad: no es suficiente comprobar únicamente la extensión del archivo. La aplicación debe decodificar, normalizar y validar la ruta final antes de realizar cualquier acceso al sistema de archivos.

Conclusión

Este laboratorio demuestra que validar únicamente la extensión de un archivo no es suficiente para proteger una aplicación frente a ataques de Path Traversal.

La combinación de secuencias ../ con el byte nulo %00 permite aprovechar diferencias en el procesamiento de la entrada entre distintas capas de una aplicación vulnerable.

El payload utilizado:

../../../../etc/passwd%00.jpg

mantiene aparentemente la extensión requerida, pero permite que un componente vulnerable procese únicamente la ruta correspondiente a /etc/passwd.
